1. Project Overview & Motivation

Q1: Summarize your project in 2 minutes.

Answer: This project designed, implemented, and evaluated a multimodal audio-visual deepfake detection system using a Cross-Modal Transformer Fusion architecture. The system processes video frames through a ResNet3D-18 encoder pretrained on Kinetics-400 and audio through a ResNet18 encoder operating on mel-spectrograms. Both modalities are fused via a 2-layer Transformer Encoder with a learnable [CLS] token, producing three independent predictions — audio authenticity, video authenticity, and joint authenticity. The model was trained on 68,851 clips from the AV-Deepfake1M++ validation split using a speaker-disjoint partition to prevent identity leakage, Focal Loss for hard-example mining, and a two-phase fine-tuning schedule. The best model (Model 3, epoch 3) achieved 93% accuracy, precision 1.000, F1 0.837, and zero false positives on a 100-video held-out test set. The deliverables include trained checkpoints, a resumable cloud-compatible training pipeline with W&B audit logging, a standalone CLI inference tool, and a Flask web interface with three tabs. The key finding is that score calibration determines deployment readiness more than raw AUC — an earlier-epoch checkpoint with lower validation AUC outperformed a higher-AUC model by 27 percentage points in threshold accuracy.

Q2: What is the main contribution of your work?

Answer: Four contributions:

  1. Speaker-disjoint evaluation protocol using GroupShuffleSplit on speaker ID, addressing the identity leakage problem documented by Rossler et al. (2019). Most prior multimodal detection work uses random splits that inflate performance metrics. My results reflect genuine manipulation detection, not face recognition.

  2. Three-head interpretable architecture producing per-modality predictions. Unlike binary-output systems (Cai et al., 2024; Yi et al., 2023), my model tells you which modality is triggering the fake verdict. The dissociation pattern — audio_modified clips get low audio scores and high video scores, visual_modified clips get the reverse — empirically validates that the architecture achieves genuine modality specialisation.

  3. Empirical finding on score calibration vs AUC: Higher validation AUC does not guarantee better threshold-based deployment performance. This is demonstrated concretely: Model 2 (AUC 0.994, accuracy 66%) vs Model 3 (AUC 0.985, accuracy 93%). Score calibration analysis via reliability diagrams is rarely reported in prior multimodal detection work.

  4. Production-ready engineering: Resumable manifest-based extraction system that survives cloud instance termination, two-phase training protecting pretrained features, W&B audit trail, and a standalone inference system with no training dependencies.

Q3: Why did you choose AV-Deepfake1M++ over other datasets like DFDC or FaceForensics++?

Answer: AV-Deepfake1M++ (Cai et al., 2025) is the most recent large-scale multimodal deepfake benchmark, containing 2 million video clips across 2,000+ speakers with four manipulation types: real, audio_modified, visual_modified, and both_modified. This four-type categorization is unique — DFDC (Dolhansky et al., 2020) only provides binary labels (real/fake), and FaceForensics++ (Rossler et al., 2019) is visual-only.

Three specific advantages: First, AV-Deepfake1M++ includes real-world perturbations (compression artifacts, variable lighting, diverse recording conditions) that make it more challenging and representative than lab-condition datasets. Second, the fake_segments temporal annotations enable future work on temporal localization of manipulation. Third, the dataset was designed for the ACM Multimedia 2025 challenge, providing a standardized benchmark and established baselines.

The practical reason for using only the validation split (68,851 clips) rather than the full training set (1M+ clips) was resource constraints — the full dataset is approximately 1.4 TB, and as a student project without institutional GPU access, downloading, storing, and processing the full dataset within the project timeline and budget was infeasible. This is acknowledged as a limitation.

Q4: How does your work differ from the AV-Deepfake1M++ baseline (DiMoDif)?

Answer: DiMoDif (Cai et al., 2025) uses cross-modal attention with temporal boundary detection as its fusion mechanism, operating over frame-aligned audio-visual features. My work differs in three architectural respects:

Aspect DiMoDif (Baseline) This Work
Fusion Cross-modal attention + temporal boundary detection Transformer Encoder with [CLS] token, 2 layers, 8 heads
Output Joint prediction + temporal boundary Three-head: audio, video, joint
Audio encoder RawNet2-style waveform processing ResNet18 on mel-spectrograms
Video encoder Similar (ResNet3D-based) ResNet3D-18 (Kinetics-400 pretrained)
Loss Not specified in detail Focal Loss (γ=2.0, α=0.25)

The [CLS] token approach follows BERT-style classification (Devlin et al., 2019) adapted for modality fusion. The three-head design provides interpretability that a binary output does not. However, direct comparison is not possible because I trained on only the validation split, while DiMoDif was trained on the full training set.

2. Literature Review

Q5: What are the key gaps you identified in the literature, and how does your work address them?

Answer: Three gaps (documented in Section 2.7 of the dissertation):

Gap 1 — Identity Leakage: (Rossler et al., 2019) demonstrated that random train/validation splits inflate deepfake detection performance because models learn to recognize faces rather than detect manipulation. When the same speaker appears in both splits, the model exploits identity features. My solution: GroupShuffleSplit on speaker ID extracted from file paths, verified zero overlap. This means my reported metrics — AUC 0.937, accuracy 93% — reflect genuine manipulation detection on unseen identities.

Gap 2 — Vision-Centric Bias: (Yi et al., 2023) noted that even multimodal detectors typically use simple feature concatenation for fusion. My solution: Transformer Encoder where audio and video tokens attend to each other through self-attention at every layer. The [CLS, video, audio] token sequence with positional embeddings allows the model to learn cross-modal relationships rather than treating modalities as independent channels.

Gap 3 — Limited Generalisation: (Dolhansky et al., 2020) documented that DFDC-winning models degraded significantly on unseen generators. My partial solution: The speaker-disjoint split addresses one dimension of this problem (identity generalization). Cross-dataset generalization remains unevaluated and is the top-priority future direction.

Q6: Why is speaker-disjoint splitting important? Can you quantify the impact?

Answer: Speaker-disjoint splitting prevents the model from learning to recognize individuals rather than detecting manipulation artifacts. Rossler et al. (2019) demonstrated this effect on FaceForensics++: models trained with random splits achieved over 95% accuracy by exploiting compression artifacts and face identity, while their true cross-manipulation generalization was much lower.

I cannot quantify the exact impact within my project because I did not run a controlled comparison of random vs speaker-disjoint splits (this would be a valuable ablation). However, published work on AV-Deepfake1M (Cai et al., 2024) and similar datasets consistently shows that random-split metrics overestimate real performance. My implementation extracts speaker IDs from file paths (e.g., source/id00015/clip.mp4 → id00015) and verifies zero overlap via assertion in data_utils.py. With 1,835 unique speakers in the validation split, GroupShuffleSplit ensures all videos from a given speaker go to exactly one partition.

Q7: How have deepfake detection approaches evolved over time?

Answer: Three phases identified in the literature (Section 2.3 of the dissertation):

Phase 1 — Visual Fidelity (2017–2019): Early work focused on visual artifacts in static frames — face warping boundaries (Li and Lyu, 2018), inconsistent eye blinking, color anomalies. Datasets were small (FaceForensics++, 1,000 videos). Models: XceptionNet (Rossler et al., 2019), MesoNet.

Phase 2 — In-the-Wild (2019–2021): Recognition that lab-condition datasets don’t generalize. Larger datasets emerged: DFDC (100K+ clips, 3,426 actors), Celeb-DF (Li et al., 2020), WildDeepfake (Zi et al., 2021). Temporal modeling via 3D CNNs and RNNs became standard. Multi-face, multi-subject scenarios addressed.

Phase 3 — Multimodal (2023–2025): Current phase. Neural TTS (NaturalSpeech 2, Shen et al., 2023) and NeRF-based talking-head synthesis (AD-NeRF, Guo et al., 2021) enable simultaneous audio and video manipulation. AV-Deepfake1M and AV-Deepfake1M++ provide large-scale multimodal benchmarks. Detection requires cross-modal architectures — the gap between audio and video coherence is now the primary detection signal.

3. Architecture & Design

Q8: Explain your Cross-Modal Transformer Fusion architecture in detail.

Answer: The architecture has three stages (49.7M total parameters, implemented in cross_modal.py → TransformerFusion class):

Stage 1 — Parallel Modality Encoding: - Video: 50 frames (2s at 25fps) at 224×224 → ResNet3D-18 (33.3M params, Kinetics-400 pretrained, 3D conv kernels process spatial + temporal jointly) → 256-d feature vector with dropout 0.4. - Audio: 2s at 16kHz → Mel-spectrogram (128 mel bins × 63 time steps, FFT window 1024, hop 512) → ResNet18 (11.7M params, ImageNet pretrained, conv1 modified from 3→1 channel) → 256-d feature vector with dropout 0.4.

Stage 2 — Transformer Cross-Modal Fusion: - Both 256-d vectors are projected to 512-d through separate Linear layers and unsqueezed to (B, 1, 512). - A learnable [CLS] token (nn.Parameter, shape 1×1×512, randomly initialized) is prepended to form the 3-token sequence: [CLS, video, audio]. - Learnable positional embeddings (shape 1×3×512) are added. - The sequence passes through a 2-layer Transformer Encoder: 8 attention heads, 2048-dim feedforward (4× hidden_dim), GELU activation, pre-norm (norm_first=True), dropout 0.4. - Self-attention allows each token to attend to all others — audio attends to video, video attends to audio, [CLS] attends to both.

Stage 3 — Three-Head Classification: - The [CLS] token’s output representation (512-d) feeds three independent Linear(512→1) layers with Sigmoid activation. - Audio Head → σ → p_audio ∈ (0,1) — “Is the audio authentic?” - Video Head → σ → p_video ∈ (0,1) — “Are the visual frames authentic?” - Joint Head → σ → p_joint ∈ (0,1) — “Is the overall video authentic?”

Why [CLS] token: Following BERT (Devlin et al., 2019), the [CLS] token aggregates information from all sequence elements through self-attention. Its final hidden state serves as a compact representation of the fused cross-modal information.

Q9: Why did you replace Wav2Vec 2.0 with ResNet18 for audio? Was it the right decision?

Answer: The switch from Wav2Vec 2.0 (Baevski et al., 2020) to ResNet18 on mel-spectrograms was driven by practical necessity, not theoretical preference.

The problem: Wav2Vec 2.0 expects clean 16kHz mono audio. The AV-Deepfake1M++ dataset contains non-standard MP4 containers with variable codecs. When librosa attempted to load audio from these files, it either: - Failed silently with zero-length arrays, or - Produced corrupted waveforms that caused Wav2Vec to output NaN features.

The solution: Switching to torchaudio with FFmpeg backend handled these corrupt containers robustly. Using mel-spectrograms + ResNet18 provided a stable feature extraction pipeline that processed 68,851 clips successfully versus the alternative of losing a significant fraction of the dataset.

Was it right? In retrospect, yes — for this specific dataset and resource context, the engineering robustness of torchaudio/FFmpeg was more impactful than Wav2Vec’s theoretical advantage in representing speech. The mel-spectrogram representation (128 bins × 63 time steps) captures sufficient spectral information for detecting TTS/VC artifacts, and ResNet18’s ImageNet pretraining provides strong initial features even for single-channel input. The audio head achieved meaningful discrimination (audio_modified clips score lower than real clips), though it was weaker than the video head — consistent with the broader finding that audio-only deepfake detection remains challenging (Yi et al., 2023).

However, I cannot claim that ResNet18 is better than Wav2Vec 2.0 — only that it was practically viable for this dataset. A controlled comparison on clean audio would be needed for a design recommendation, which is future work.

Q10: Why use ResNet3D-18 instead of a 2D CNN for video?

Answer: 2D CNNs (like XceptionNet, MobileNetV3) process each video frame independently and then aggregate frame-level predictions — typically through averaging or an LSTM. This approach can detect spatial artifacts (blur, color inconsistencies, face boundary artifacts) but cannot model temporal dynamics — how pixels move across consecutive frames.

Lip-synced deepfakes (the dominant manipulation type in AV-Deepfake1M++) are created by synthesizing the lip region of each frame to match a target audio track. The synthesis is spatially convincing on individual frames, but the trajectory of lip movement across frames often shows subtle temporal inconsistencies — unnatural acceleration, micro-jitter, or motion patterns that differ from natural speech-driven articulation.

ResNet3D-18 (Tran et al., 2018) uses 3D convolutional kernels (e.g., 3×3×3) that jointly process spatial dimensions (height, width) and temporal dimension (frame sequence). The Kinetics-400 pretraining (Kay et al., 2017) on 400 human action categories — including talking, singing, and gesturing — provides features relevant to human motion analysis. The 50-frame input window at 25fps captures 2 seconds of lip motion, which is sufficient for modeling the temporal signature of natural speech.

Q11: Explain Focal Loss and why you chose it over Binary Cross-Entropy.

Answer: Focal Loss (Lin et al., 2018) extends Binary Cross-Entropy with a modulating factor (1−p_t)^γ:

FL(p_t) = −α_t(1−p_t)^γ log(p_t)

where p_t = p if y=1, else 1−p (the model’s confidence in the correct class).

Mechanism: When the model is confident and correct (p_t → 1), the modulating factor (1−p_t)^γ → 0, down-weighting that example’s contribution to the loss. When the model is uncertain (p_t ≈ 0.5), the factor ≈ 0.5^γ, preserving the full loss signal. With γ=0, this reduces to standard BCE. With γ=2.0 (my setting), the down-weighting is quadratic.

Why this matters for deepfake detection:

  1. Many easy examples: Real videos where both modalities are clearly authentic produce very confident predictions (p_t close to 1). Without Focal Loss, these continue to contribute to the gradient even after the model has learned them well, potentially overwhelming the signal from hard cases. Focal Loss automatically down-weights them.

  2. Hard ambiguous cases matter most: Audio_modified clips where the genuine video stream counteracts the fake audio signal produce uncertain predictions near 0.5. These are exactly the cases where the model needs the most training. Focal Loss preserves (and effectively amplifies) gradient signal on these examples.

  3. Class imbalance handling via α: The α=0.25 parameter provides additional class rebalancing, giving higher weight to the minority class (typically real videos).

Without a controlled ablation (Focal Loss vs BCE, same architecture, same data), I cannot quantify the exact contribution. This is the highest-priority ablation for future work. My qualitative observation: training converged rapidly with stable loss curves, and Model 3 achieved zero false positives — a desirable characteristic for detection systems — but I cannot attribute this specifically to Focal Loss.

Q12: Why three heads (audio, video, joint) instead of just a binary output?

Answer: The three-head design serves three purposes:

1. Interpretability: A binary output tells you whether a video is fake but not why. The three-head output tells you which modality is suspicious — is the audio fake while the video is real (audio_modified)? Is the video fake while the audio is real (visual_modified)? This per-modality breakdown is valuable for forensic analysis and user trust.

2. Architectural validation: The three-head design enables empirical verification that the model genuinely learns modality-specific features rather than collapsing to a single signal. The dissociation pattern — audio_modified clips get low audio scores but high video scores, visual_modified clips get opposite — confirms that the audio and video heads are independently learning and not just regurgitating the same fused representation.

3. Training signal: The intermediate loss on the audio and video heads provides additional gradient signal during training. The combined loss function (L = 0.4×L_audio + 0.4×L_video + 0.8×L_joint) encourages both modality encoders to produce discriminative features independently, which benefits the final joint prediction even if only the joint head is used at inference time.

The joint head labels use AND logic: a video is “real” (joint label = 1) only if both audio AND video are real. This maps to the detection task — a video with fake audio but real video (audio_modified) is a deepfake and should be detected as such.

4. Implementation & Engineering

Q13: Describe your training pipeline and the key engineering challenges.

Answer: The pipeline (orchestrated by main.py) follows five stages:

Stage 1 — Data Download: download_data.py pulls the AV-Deepfake1M++ validation split from Hugging Face. The dataset is distributed as multi-part ZIP archives. Automatic extraction and verification handle incomplete downloads.

Stage 2 — Metadata Loading & Speaker Split: data_utils.py → load_metadata() reads val_metadata.json (77,326 entries). sample_videos() extracts speaker IDs from file paths and applies GroupShuffleSplit with 80/20 split, verifying zero speaker overlap. The pipeline also validates that each video has non-zero audio_frames and video_frames (211 flagged, 8,264 missing from disk), leaving 68,851 usable clips.

Stage 3 — Feature Extraction: extract_all_features() distributes work across 28 CPU workers using fork-based multiprocessing. Each worker opens a video with torchaudio/FFmpeg (audio) and OpenCV (video frames), extracts features, and saves as individual .pt files. A manifest system (train_manifest.json, val_manifest.json) tracks successfully extracted features and failures (*_failed.json). Extraction is incremental — workers save progress every 500 successes and skip already-processed files on restart. This system proved essential when cloud instances terminated unexpectedly — without it, the full extraction (~6–8 hours) would need to restart from scratch.

Stage 4 — Training: train_utils.py → train_model() implements two-phase fine-tuning with Focal Loss, AdamW optimizer, ReduceLROnPlateau scheduler, gradient clipping, and W&B logging. Checkpoints save model state, optimizer state, scheduler state, and all random number generator states at each epoch, enabling full training resumption. Model selection uses validation joint AUC as the monitoring metric.

Stage 5 — Evaluation: evaluate_model() in main.py loads the best checkpoint, runs 3-window inference on all validation videos, and computes per-head AUC, per-type accuracy, confusion matrices, and scatter plots. compare_models.py provides multi-model comparison with reliability diagrams.

Key engineering challenges: - Corrupted MP4 containers: librosa failed silently; torchaudio with FFmpeg backend resolved this. - Cloud instance termination: Vast.ai instances terminate without notice. Resumable manifests and checkpoint-based training ensured zero data loss. - File transfer corruption: Model 1’s checkpoint was corrupted during SCP download. A file-size check before terminating the instance was the fix. - 28-worker multiprocessing: Fork-based parallelism required careful handling of file descriptors and GPU tensor transfers (extraction is CPU-only, training uses GPU via DataLoader).

Q14: How did you handle the dataset size and storage constraints?

Answer: Three strategies:

1. Validation split only: Instead of the full training set (~1M+ clips, ~1.4 TB), I used only the validation split (77,326 metadata entries, 68,851 usable clips). This reduced storage requirements from terabytes to approximately 140 GB for the raw videos plus extracted features.

2. Pre-extraction to disk: Video and audio features (ResNet3D-18 embeddings and mel-spectrograms) are extracted once and saved as individual .pt files (~500 KB each). This is a one-time cost. Training uses a lazy-loading PyTorch Dataset that reads features from disk on demand, avoiding repeated video decoding. The 68,851 feature files occupy approximately 35 GB.

3. Resumable manifests: The manifest-based extraction system enables incremental processing. If storage fills or the instance terminates, extraction resumes from the last saved progress point. The *_failed.json manifest tracks clips that could not be processed (corrupted, missing, codec issues), preventing repeated attempts.

Storage footprint: Raw videos (~140 GB) + extracted features (~35 GB) + checkpoints (~2 GB) + logs (~1 GB) ≈ 178 GB total. This fit within the 500 GB SSD of a Vast.ai instance.

Q15: What is your two-phase training strategy and why is it necessary?

Answer: Two-phase training (implemented in train_utils.py, controlled by freeze_epochs in config.py) separates encoder protection from fine-tuning:

Phase 1 (frozen encoders): ResNet3D-18 and ResNet18 encoder parameters are frozen (requires_grad = False). Only the Transformer fusion module and classification heads are trainable. Duration: max(1, round(epochs × 0.25)) = 2–3 epochs.

Rationale: The pretrained weights (Kinetics-400 for video, ImageNet for audio) encode rich general features. At the start of training, the randomly-initialized fusion module produces poor, noisy gradients. If encoders are trainable from epoch 1, these poor gradients can rapidly destroy pretrained features through large weight updates — a form of catastrophic forgetting. Phase 1 protects the encoders while the fusion module learns to relate their outputs. The frozen encoders act as fixed feature extractors, providing stable 256-d embeddings that the fusion module learns to combine.

Phase 2 (fine-tuning): All parameters unfrozen. Encoder learning rate set to 1e-5 (10× lower than fusion module’s 1e-4).

Rationale: The lower learning rate for encoders allows domain adaptation (from action recognition/object classification to deepfake detection) while preventing large updates that would erase pretrained knowledge. The 10× ratio follows standard transfer learning practice for fine-tuning deep networks.

Evidence for necessity: Model 1 (Phase 1 only, 1 epoch) achieved validation AUC of 0.663 — significantly below the ≥0.985 achieved by all Phase-2-trained models. This demonstrates that cross-modal representations require encoder adaptation to the target domain. Without Phase 2, the frozen encoders alone cannot provide sufficiently task-relevant features.

Q16: How does the data loading and augmentation work?

Answer: Feature extraction produces .pt files on disk. Training uses a PyTorch Dataset (PreExtractedDataset in data_utils.py) that: 1. Reads the manifest JSON to get file paths. 2. Lazy-loads .pt files on demand via torch.load(). 3. Applies augmentations on-the-fly.

Audio augmentations: - SpecAugment (Park et al., 2019): Random frequency masking (up to 20 mel bins) and time masking (up to 15 time steps) applied to the mel-spectrogram. This simulates partial frequency loss and temporal dropout, improving robustness to audio compression and recording artifacts. - Implemented via torchaudio.transforms.FrequencyMasking and TimeMasking.

Video augmentations: - Random horizontal flip (50% probability). - Brightness jitter (±0.2). - Contrast jitter (0.8–1.2). - Applied via torchvision.transforms on each frame independently.

No augmentations for validation/inference — only training.

Multiwindow inference: During evaluation, extract_multiple_windows() samples 3 different 2-second windows from each video. Predictions are averaged across windows. For fake videos, windows are preferentially sampled near the fake_segments temporal annotations (when available) to maximize the chance of capturing manipulated content.

Q17: Describe your web interface and inference system.

Answer: The system has two interfaces (Objective 6):

CLI (inference.py): - Loads model weights independent of training dependencies (no config.py, train_utils.py needed). - Supports single video (--video) or folder (--video_dir) modes. - Outputs to console or CSV (--output). - Device selection (--device cpu or --device cuda). - Uses the same FEATURE_CONFIG parameters as training (2s clips, 50 frames, 128 mel bins, 63 time steps).

Web Interface (Flask, web/app.py): - Analyze tab: Drag-and-drop video upload, model selector dropdown (Models 2, 3, 4), real-time verdict with three per-head probability scores. Video is processed by backend calling inference.py functions. - Compare tab: Two models run on the same uploaded video. Side-by-side display of model names, per-head scores, verdicts. Agree/disagree badge (green check / red X) summarizes concordance. - History tab: SQLite-backed table displaying all past analyses (filename, model, verdict, scores, timestamp). Features: per-entry delete, bulk clear. - Single-page application (no page reloads), Bootstrap-styled, vanilla JavaScript.

Backend architecture: Flask serves static files and provides REST endpoints (POST /analyze, POST /compare). Model weights are loaded once at server startup (global variable). Video files are saved temporarily, processed, and cleaned up after inference.

Q19: Why did Model 1 fail?

Answer: Model 1 achieved validation AUC 0.663 after a single epoch of Phase-1-only training (frozen encoders). Two factors:

1. Insufficient training: One epoch of Phase 1 — where only the randomly-initialized fusion module and classification heads are trainable — is insufficient for the fusion module to learn meaningful cross-modal relationships. The frozen encoders produce fixed features, and the fusion module needs multiple epochs to learn how to combine them for classification.

2. Underfit classifier: The prediction pattern (all outputs in the 0.23–0.35 range, always predicting FAKE) is characteristic of an underfit classifier predicting the majority class. The fusion module had not converged — its weights were still close to random initialization, producing compressed, non-discriminative representations.

Additional issue: The checkpoint file was corrupted during SCP download from the cloud instance. File size verification before terminating the instance would have caught this — a practical lesson in infrastructure management.

Lesson: Phase 2 fine-tuning is essential. Model 1 serves as a valuable baseline demonstrating that frozen encoders alone cannot solve the detection task — cross-modal representations require encoder adaptation to the target domain.

Q20: How did you handle hyperparameter selection?

Answer: Hyperparameters were not systematically tuned. This is a significant limitation acknowledged in the dissertation (Section 5.5).

Approach taken: - Values were set based on standard practice in the literature and initial trial runs. - freeze_epochs and patience are auto-computed as fractions of the total epoch budget (freeze_epochs = max(1, round(epochs × 0.25)), patience = max(5, round(epochs × 0.30))). - W&B Bayesian sweep configuration (SWEEP_CONFIG in main.py) was prepared but never executed due to the 5-epoch budget constraint — sweeps require many short runs to be informative. - All runs used the same hyperparameters: feature_dim=256, hidden_dim=512, dropout=0.4, focal_gamma=2.0, focal_alpha=0.25.

Justification for specific values: - dropout=0.4: Higher than typical (0.2–0.3) because the dataset is large and generalization is the primary concern. - hidden_dim=512 = 2 × feature_dim: Gives the fusion module sufficient capacity without being excessive. - focal_gamma=2.0: Standard value from the Focal Loss paper (Lin et al., 2018). - batch_size=8: Largest that fits in 10GB VRAM per GPU with 50-frame video inputs.

The W&B sweep configuration (prepared but not run) explores: focal_gamma ∈ {0.5, 1.0, 2.0, 3.0}, focal_alpha ∈ {0.1, 0.25, 0.5, 0.75}, dropout ∈ [0.2, 0.5], hidden_dim ∈ {256, 512, 1024}, learning_rate ∈ [1e-5, 1e-3] (log-uniform), freeze_epochs ∈ {4, 8, 12}, weight_decay ∈ [1e-5, 1e-3].

6. Results & Evaluation

Q21: Interpret your main results. What is the significance of Model 3 vs Model 2?

Answer: The most important result is the dissociation between validation AUC and threshold-based accuracy.

Metric Model 2 (epoch 5) Model 3 (epoch 3) Difference
Val Joint AUC 0.994 0.985 M2 +0.009
Test AUC 0.919 0.937 M3 +0.018
Test Accuracy (τ=0.5) 66% 93% M3 +27pp
Precision — 1.000 —
False Positives — 0 —

What happened: Model 2 ranked videos correctly almost all the time (AUC 0.994 means 99.4% of random real/fake pairs are correctly ordered). But its probability scores were poorly calibrated — many scores clustered near 0.5, the decision boundary. At τ=0.5, a small perturbation in score (0.49 vs 0.51) flips the classification, producing many errors despite correct relative ordering.

Model 3, saved at the first fine-tuning epoch, produced better-calibrated scores — real videos received confident high scores (0.7–0.95) and fake videos received confident low scores (0.05–0.3). The wider score spread means the τ=0.5 threshold cleanly separates the classes.

Why this happens: Extended training (epochs 4–5) can cause score compression — the model overfits to training examples near the boundary, pulling their predicted probabilities toward 0.5. This phenomenon is related to overfitting and has been documented in neural network calibration literature (Guo et al., 2017). The validation AUC can remain high or even improve because ranking order is preserved, but the absolute probability values become less trustworthy.

Practical significance: For real-world deployment with a fixed decision threshold, calibration quality matters more than AUC. Model 3 with 93% accuracy and zero false positives is deployable; Model 2 with 66% accuracy is not — despite its superior AUC.

Caveat: This observation is based on n=3 loadable checkpoints from 5-epoch training runs. It is hypothesis-generating, not confirmatory. Whether extended training (20+ epochs) would reverse, persist, or stabilize this pattern is unknown.

Q22: Explain the per-type accuracy results. Why is audio_modified the hardest?

Answer: Model 3’s per-type joint accuracy at τ=0.5:

Type Accuracy
real 100%
visual_modified ~92%
both_modified ~92%
audio_modified ~88%

Why audio_modified is hardest: The three-head architecture produces independent scores per modality. For an audio_modified video: - The video head sees genuine, unmodified frames and outputs a high score (e.g., 0.85) — “the video looks real.” - The audio head detects TTS/VC artifacts in the mel-spectrogram and outputs a low score (e.g., 0.25) — “the audio sounds fake.” - The joint head must reconcile these conflicting signals. Its output lands somewhere between the two — closer to the 0.5 boundary than either single-modality prediction.

The genuine video signal counteracts the audio head’s fake signal in the fused representation, pushing the joint prediction toward the decision boundary. This is by design — the joint head is supposed to weigh both modalities — but it means audio_modified detection is inherently more challenging than both_modified (where both modalities provide consistent fake evidence) or visual_modified (where the video encoder, which is stronger than the audio encoder, provides the primary fake signal).

Why visual_modified is easier: ResNet3D-18 processes 50 frames as a spatiotemporal volume. Lip-region synthesis in visual_modified clips produces temporal inconsistencies — unnatural motion trajectories, micro-jitter, or discontinuities — that 3D convolutions are well-suited to detect. The Kinetics-400 pretraining on human action categories provides relevant features for analyzing human motion.

The asymmetry (audio_modified harder than visual_modified) suggests that the mel-spectrogram + ResNet18 audio encoder is less sensitive to TTS/VC artifacts than the ResNet3D-18 video encoder is to visual artifacts. This is consistent with prior work noting that audio-only deepfake detection remains challenging (Yi et al., 2023).

Q23: What do the calibration curves show, and why are they important?

Answer: Calibration curves (reliability diagrams, plot_calibration_curves.py) plot predicted probability against observed accuracy:

  • X-axis: Predicted probability, binned into deciles (0–0.1, 0.1–0.2, …, 0.9–1.0).
  • Y-axis: Observed accuracy within each bin — the fraction of videos in that probability range that were truly real.
  • Diagonal: Perfect calibration — a prediction of 0.8 should be correct 80% of the time.

Model 3’s curve closely follows the diagonal — it is well-calibrated. A Model 3 score of 0.95 means the video is real approximately 95% of the time. A score of 0.10 means the video is real approximately 10% of the time (i.e., 90% likely fake).

Model 2’s curve deviates, especially in the middle range (0.4–0.6). The model is underconfident on real videos and overconfident on some fakes. This poor calibration explains the 66% accuracy at τ=0.5 — many real videos score just below 0.5 and many fake videos score just above, despite correct relative ordering.

Why calibration matters for deployment: 1. Threshold-based decisions: Most deployed systems use a fixed threshold. If scores near 0.5 are unreliable, threshold accuracy degrades regardless of AUC. 2. Confidence interpretation: Users interpret scores as confidence. A well-calibrated model’s 0.95 genuinely means “95% confident.” A poorly-calibrated model’s 0.95 might only be correct 70% of the time. 3. Cost-sensitive decisions: In high-stakes applications (legal evidence, content moderation), knowing the actual reliability of predictions is essential for setting appropriate decision thresholds.

Methodology: Calibration analysis via reliability diagrams, following (Guo et al., 2017; Niculescu-Mizil and Caruana, 2005). This analysis is rarely reported in prior multimodal deepfake detection work, making it a methodological contribution of this project.

Q24: How reliable are your results given the 100-video test set?

Answer: Not statistically reliable. The test set contains only 25 videos per manipulation type. A single misclassification changes per-type accuracy by 4 percentage points. Confidence intervals around the reported test AUC of 0.937 would be approximately ±0.05 at 95% confidence (using DeLong’s method for AUC variance estimation).

What can be concluded: - The model clearly outperforms random chance (AUC > 0.5 by a wide margin). - The relative ranking of models (M3 > M4 > M2 by test accuracy) is suggestive but not statistically significant. - Zero false positives in Model 3 is encouraging but could change with a single classification — if one more fake video scored just below 0.5, precision would change. - Per-type accuracy differences (audio_modified at 88% vs visual_modified at 92%) may not be statistically significant given n=25 per type.

What cannot be concluded: - The exact performance level (93% ± ?). - That Model 3 is definitively better than Model 4 for all possible held-out speakers. - That the per-type accuracy ordering would persist on a larger, more diverse test set.

Mitigation: All conclusions are qualified with this limitation. The results are presented as observations from a small experiment rather than as established findings. A test set of at least 500 videos per manipulation type (2,000 total) would be needed for reliable estimates, as recommended by Dolhansky et al. (2020) for deepfake detection evaluation.

Q25: What metrics did you use and why? What are their limitations?

Answer:

Metric What it measures Why used Limitation
AUC Ranking ability (threshold-independent) Standard in detection literature; handles class imbalance Says nothing about threshold performance; a model with AUC 0.99 can fail at any specific threshold
Accuracy (τ=0.5) Correct classifications at default threshold Intuitive; practical deployment metric Highly dependent on threshold choice; 0.5 may not be optimal
Precision Fraction of fake predictions that are truly fake Critical for low-FP applications (legal, moderation) Doesn’t measure recall — a model predicting “real” always has undefined precision but no utility
F1 Score Harmonic mean of precision and recall Balances FP and FN Assumes equal cost for FP and FN, which is rarely true in practice
Calibration curves Alignment of predicted probabilities with observed correctness Assesses deployment readiness Requires binned data; sensitive to binning strategy

What I did NOT use but should have: - t-DCF (tandem Detection Cost Function): Standard in speaker verification (ASVspoof). Measures combined cost of missed detections and false alarms with application-specific cost weights. More relevant for deployment than AUC or accuracy. - ECE (Expected Calibration Error): A single-number summary of calibration quality that would complement the reliability diagrams.

Recommendation for future evaluation: Report AUC for comparability with literature, but also report t-DCF or ECE for deployment relevance. Calibration curves should be standard practice in detection papers.

7. Critical Analysis & Tough Questions

Q26: You trained on only the validation split and evaluated on 100 videos. Why should anyone trust these results?

Answer: This is a fair and important criticism. The honest answer is: these results should be treated as preliminary observations from a resource-constrained student project, not as established findings suitable for publication or deployment.

Mitigating factors: 1. Speaker-disjoint split: Despite the small scale, the evaluation protocol is rigorous — zero speaker overlap between training and test sets. The results reflect genuine generalization to unseen identities, which is a stricter test than many published benchmarks that use random splits. 2. Internal consistency: The finding that score calibration degrades with extended training (M3 > M4 despite same session) is internally consistent and matches known neural network calibration behavior (Guo et al., 2017). It is a plausible hypothesis even if not statistically confirmed. 3. Qualitative architectural insights: The modality dissociation pattern (audio_modified = low audio score + high video score) is a qualitative finding that depends on architecture design, not test set size. It demonstrates the three-head architecture works as designed, regardless of the exact accuracy numbers.

What I would do differently with more resources: - Train on the full AV-Deepfake1M++ training split (1M+ clips). - Evaluate on the official challenge test set with thousands of videos. - Run 5-fold cross-validation with different speaker partitions. - Report confidence intervals on all metrics. - This is all future work (Section 6.4).

Q27: Without ablation studies, how do you know which component contributed to performance?

Answer: I don’t. This is the most significant limitation of the project (Section 5.5).

What I can say: - The full system works — 93% accuracy, zero false positives. This is a valid engineering result. - Phase 2 fine-tuning is demonstrably essential — the ablation exists in the form of Model 1 (Phase 1 only, AUC 0.663 vs ≥0.915). - The three-head architecture shows qualitative evidence of modality specialisation via the dissociation pattern. - The Transformer fusion’s advantage over MLP fusion is not demonstrated — this requires a controlled comparison.

What I cannot say: - Whether Focal Loss improves over BCE. - Whether Transformer fusion improves over MLP or simple concatenation. - Whether ResNet3D-18 improves over a 2D CNN + temporal pooling. - Whether full-frame encoding improves over lip-region crops.

My defense: Ablation studies require controlled experiments that keep all variables constant except the one being tested. This means multiple full training runs per ablation target. With each training run costing ~$15–25 and requiring 6–8 hours, a comprehensive ablation study (3 components × 2 variants each = 6 extra runs = $90–150) exceeded the cloud GPU budget for this project. The dissertation explicitly identifies this as the highest-priority future work and does not claim attribution to specific components.

Q28: Your test set was only 100 videos from the same dataset split. Doesn’t this mean your results could be highly optimistic?

Answer: Yes, this is a genuine concern. There are two separate issues:

1. Test set size (statistical reliability): With n=100 (25 per type), the confidence intervals are wide. A single misclassification changes accuracy by 1 percentage point overall and 4 percentage points per type. This is addressed in Q24.

2. Same-distribution evaluation (generalization): Training and testing on different random splits of the same dataset (even with speaker-disjoint partitioning) is not as rigorous as testing on a completely different dataset with different recording conditions, generators, and speakers. Deepfake detectors are known to overfit to dataset-specific artifacts — lighting conditions, compression codecs, camera models, background environments — that are shared across splits within the same dataset (Dolhansky et al., 2020).

Mitigation: The speaker-disjoint split addresses identity overfitting (same person in train and test), but not dataset overfitting (same recording pipeline, same codecs, same generators across the entire dataset). Cross-dataset evaluation on FakeAVCeleb or DFDC would test this, and it is the second-priority future direction.

Honest assessment: The 93% accuracy on the test set should be interpreted as “the model learned to detect manipulations produced by the AV-Deepfake1M++ generation pipeline, on speakers not seen during training” — not as “the model can detect any deepfake from any source.” This distinction is important and is clearly stated in the dissertation’s limitations section.

Q29: You claim “zero false positives” but with only 25 real videos in the test set, this could be coincidence. What’s the lower bound?

Answer: Correct. With 25 real test videos, “zero false positives” means the observed false positive rate is 0/25 = 0%. But the true false positive rate could be as high as ~11.3% at a 95% confidence level, based on the rule of three: with 0 successes in n trials, the 95% CI upper bound is approximately 3/n.

Calculation: 3/25 = 0.12, so the 95% confidence interval for the false positive rate is approximately [0%, 12%]. This means the true false positive rate could be anywhere from 0% to 12% — a wide range.

What this means: The finding “zero false positives” should be presented as “zero false positives observed on a 25-real-video test set” — not as “the model produces zero false positives in general.” With a test set of 25 real videos, this is a preliminary observation, not a deployment guarantee. A test set of at least 500 real videos would be needed to establish a false positive rate with reasonable confidence.

This limitation is documented in Section 5.5 of the dissertation.

Q30: Your work claims interpretability via three heads, but how interpretable are the scores really to a non-expert?

Answer: This is an important scope question. The three-head output provides modality-level interpretability: it tells you which modality (audio, video, or both) is driving the fake signal. This is a meaningful improvement over binary output (“this video is fake”), but it is not explainable AI in the sense of highlighting specific regions or time segments.

What it can tell you: - “This video’s audio is likely fake, but the video appears genuine” → audio_modified detection. This is actionable — it tells a forensic analyst to focus on the audio track. - “Both audio and video appear manipulated” → both_modified detection. Higher confidence since evidence from both modalities agrees.

What it cannot tell you: - Which specific frames or audio segments contain the manipulation. - What type of artifact (spectral irregularity, motion inconsistency) was detected. - Why a particular score was assigned.

The gap: True interpretability for deepfake detection would involve attention maps over video frames (showing which lip regions triggered the detection) and saliency maps over spectrograms (showing which frequency bands or time segments contained TTS artifacts). These are not implemented in the current system. The three-head architecture is a first step toward interpretability — showing which modality is affected — but should not be confused with full explainability.

Q31: If you had to do this project again, what would you do differently?

Answer: Five changes in priority order:

  1. Start with institutional GPU access: Cloud GPU costs were the binding constraint that prevented hyperparameter sweeps, ablation studies, and extended training. With institutional GPUs (free), I would run 20+ epochs, sweep hyperparameters using W&B Bayesian optimization, and conduct the ablation studies that are now listed as future work. The dollar cost was approximately $60–80 total for a handful of 5-epoch runs — this is a tiny absolute amount but a real constraint for a student.

  2. Run ablation studies concurrently with development: Instead of designing the full system and only then testing, I would run small-scale ablations on subsets of the data early in the project. For example: train on 5,000 clips with Focal Loss vs BCE, Transformer vs MLP, with 5 epochs each. This would provide preliminary evidence for design decisions within the project timeline.

  3. Verify checkpoint integrity before terminating instances: Model 1 was corrupted during SCP download from a Vast.ai instance. A simple ls -la file size check before stopping the instance would have caught the truncated transfer. This is a trivial change that lost an entire training run’s checkpoint.

  4. Use the full training split: The validation split (68,851 clips) was used because it fit within disk constraints and download time. With more planning and storage, using even a subset of the full training split (e.g., 200K clips randomly sampled) would provide more diverse training data and likely better generalization. The Hugging Face dataset supports partial downloads by file pattern.

  5. Report statistical confidence: All metrics should include confidence intervals. AUC confidence intervals can be computed via DeLong’s method (implemented in sklearn/scipy). Accuracy confidence intervals use binomial proportion. This would make the results more honest and prevent overinterpretation of small test sets.

8. Limitations & Future Work

Q32: What are the three most important limitations of your work?

Answer:

1. No ablation studies (most important): Cannot attribute performance to any individual architectural component. The model achieves 93% accuracy, but I cannot say whether Focal Loss, Transformer fusion, ResNet3D-18, or the two-phase training schedule individually contributed to this result, or whether a simpler system (BCE + MLP fusion) would perform similarly.

2. Small, same-distribution test set: 100 videos from the same dataset split. This combines two problems: statistical unreliability (wide confidence intervals) and lack of cross-dataset generalization testing (unknown performance on videos from different generators or recording conditions). The 0 false positives on 25 real videos is particularly fragile — a 95% CI upper bound of ~12% FPR.

3. 5-epoch training cap: Models 2 and 4 were halted while validation AUC was still improving (0.994 at epoch 5, 0.992 at epoch 4). It is unknown whether extended training would improve calibration, change the M3 > M2 ranking, or produce continued score compression. The finding that early-epoch checkpoints outperform later-epoch ones may be an artifact of limited training — it might reverse, persist, or stabilize with 20+ epochs.

Other significant limitations: Single dataset, fixed 2-second window, no temporal localization, validation split only.

Q33: What are your top three future work priorities and why?

Answer:

1. Ablation studies: Most urgent. Without controlled experiments comparing Focal Loss vs BCE, Transformer vs MLP fusion, full-frame vs lip-region crops, and single-modality vs multimodal training, the project cannot make evidence-based architectural recommendations. This is the foundation for all other future work — you cannot improve what you haven’t measured.

2. Cross-dataset evaluation: Most practically relevant. Testing on FakeAVCeleb, DFDC, or FaceForensics++ directly measures the generalization that matters for real-world deployment. A model achieving 93% on AV-Deepfake1M++ but 60% on FakeAVCeleb is not useful. This evaluation would also quantify how much the speaker-disjoint split improves over random splits in a cross-dataset setting — a contribution relevant to the broader detection community.

3. Full dataset training: Most impactful for performance. Using the full AV-Deepfake1M++ training split (1M+ clips, 2,000+ speakers) would expose the model to the full diversity of manipulation generators, speaker identities, and recording conditions. This is the most direct path to improved generalization within the AV-Deepfake1M++ domain.

Other priorities (Q34 addresses temporal localization): Threshold optimization for cost-sensitive deployment, longer training with hyperparameter sweeps, improved experiment management infrastructure.

Q34: How would you extend this work to temporal localization of manipulation?

Answer: The AV-Deepfake1M++ dataset includes fake_segments annotations — ground-truth temporal boundaries (start_time, end_time) of manipulated regions within each video clip. The current system only classifies the entire clip; temporal localization would identify when manipulation occurs.

Approach: 1. Sliding window with overlap: Instead of a single 2-second window, slide a window across the entire video with 50% overlap. Run each window through the model. Windows overlapping with fake_segments should produce low joint scores; windows in real segments should produce high scores. Plot the joint score as a time series over the video duration.

  1. Frame-level architecture: Replace the clip-level classification heads with temporal prediction heads. The Transformer fusion module could output per-token predictions (not just [CLS]), and the video encoder could output frame-level features. Train with temporal labels derived from fake_segments.

  2. Evaluation metric: Temporal IoU (Intersection over Union) between predicted manipulation intervals and ground-truth fake_segments. Standard metric in temporal action localization.

Challenges: The current architecture uses a [CLS] token for classification — extending to per-frame predictions requires architectural changes. The 2-second feature extraction window limits temporal resolution — frame-level prediction would need sub-second windows. Training would require videos with diverse temporal manipulation patterns, which may be underrepresented in the dataset.

9. Ethics, Impact & Practicality

Q35: What are the ethical implications of your work? Could it be misused?

Answer: This project falls on the detection side of the deepfake arms race — its purpose is harm mitigation, not harm creation. The ethical considerations are:

Positive ethical impact: - Harm reduction: Every improvement in detection capability makes deepfake-based fraud, disinformation, and non-consensual content harder to execute successfully. - Digital forensics tool: Provides per-modality interpretability that can assist human analysts in understanding why a video was flagged. - Transparent methodology: The code is modular, documented, and reproducible, supporting open research in detection.

Potential misuse concerns: - Adversarial training: Detection models can be used adversarially — a generator can train against the detector to produce more convincing fakes. This is the fundamental cat-and-mouse dynamic of the deepfake field (Chesney and Citron, 2019). My model, being trained on a specific dataset, would be easier to adversarially target than a more general system. - Over-reliance: A 93% accurate system with zero observed false positives might encourage over-reliance in high-stakes contexts (legal evidence, content moderation). The confidence intervals (Q29) show this would be dangerous — the true false positive rate could be as high as 12%. - Dataset consent: The AV-Deepfake1M++ dataset involves real individuals whose likenesses were modified to create deepfake content. The dataset creators obtained consent, and the terms of use explicitly prohibit using the data for generating non-consensual deepfake content. I used the dataset exclusively for detection research within the published terms.

Mitigation in the dissertation: The ethical approval process (CN6000 Internal Ethical Approval) confirmed that secondary analysis of a publicly available benchmark dataset requires no additional ethical clearance. The dataset’s consent framework (Appendix D) and my compliance with its terms are documented.

Recommendation: Any deployment of this system should include explicit disclaimers about confidence intervals, dataset limitations, and the ongoing adversarial dynamic between generators and detectors.

Q36: Is your system practically deployable? What would need to change?

Answer: Partially. The system has several deployable characteristics but also significant gaps.

Deployable aspects: - Standalone inference (inference.py): No training dependencies, single-file execution, CPU-compatible model loading. - Web interface with history: SQLite-backed audit trail, model comparison, user-friendly UI. - Resumable pipeline: The training infrastructure is production-quality — checkpointing, W&B logging, crash recovery. - Interpretable output: Three-head scores tell users which modality triggered detection.

Gaps preventing production deployment:

Gap Severity Fix
Unknown cross-dataset generalization Critical Evaluate on diverse datasets; retrain if needed
No confidence intervals High Report per-prediction uncertainty via MC Dropout or ensemble
100-video validation only High Validate on larger, diverse test set
No adversarial robustness testing High Test against adversarially perturbed videos
Fixed 2-second window Medium Implement sliding window or variable-length processing
No threshold optimization Medium Calibrate threshold on cost-weighted validation set

Minimal viable deployment path: 1. Retrain on full AV-Deepfake1M++ training set. 2. Evaluate on at least 2 held-out datasets (FakeAVCeleb, DFDC). 3. Optimize threshold for target application (low FP for content moderation; low FN for forensic triage). 4. Add uncertainty quantification (MC Dropout or deep ensemble). 5. Containerize (Docker) with GPU support for cloud deployment.

Q37: How does your system compare to commercial deepfake detection tools?

Answer: This is difficult to answer definitively because commercial tools (Deepware, Sensity, Reality Defender) do not publish their architectures, training datasets, or benchmark results.

Likely advantages of commercial systems: - Trained on much larger and more diverse datasets (proprietary, continuously updated). - Tested on real-world, in-the-wild deepfakes, not just benchmark datasets. - Include additional detection signals: metadata analysis (compression artifacts, EXIF), provenance tracking (C2PA), blockchain verification. - Team-scale engineering: dedicated ML engineers, ongoing model updates, infrastructure at scale.

Likely advantages of my system: - Interpretable per-modality output: Commercial tools typically provide a single score. My three-head output tells you which modality is affected — useful for forensic triage. - Transparent methodology: Every architectural decision, hyperparameter, and limitation is documented. Commercial tools are black boxes. - Academic rigor: Speaker-disjoint evaluation, calibration analysis, explicit limitation documentation — practices not guaranteed in proprietary systems.

Honest assessment: My system is a research prototype demonstrating architectural ideas (cross-modal Transformer fusion, three-head interpretability, score calibration analysis). It is not competitive with well-funded commercial detectors on raw detection performance, nor is it intended to be. Its value is in the methodology — the speaker-disjoint evaluation protocol, the calibration analysis, the per-modality interpretability — rather than in absolute performance metrics.

Q38: What is the broader significance of score calibration in deepfake detection?

Answer: Score calibration is underappreciated in the deepfake detection literature. Most papers report AUC and accuracy at τ=0.5, but rarely show reliability diagrams or discuss calibration quality. My project demonstrates that calibration can be the difference between a deployable and non-deployable model — Model 2 and Model 3 have nearly identical AUC (0.994 vs 0.985) but 27 percentage points apart in threshold accuracy.

Why this matters for the field: 1. AUC can be misleading: AUC measures ranking, not score quality. A model can rank every video correctly while producing scores useless for threshold-based decisions. AUC alone is insufficient for deployment readiness assessment. 2. Calibration degrades with training: The M3 (epoch 3) > M4 (epoch 5) finding suggests that extended training can improve AUC while degrading calibration — a pattern consistent with Guo et al. (2017). Practitioners monitoring only AUC during training may unknowingly deploy poorly-calibrated models. 3. Cost-sensitive deployment needs calibration: Different applications have different error costs. Content moderation prioritizes precision (low FP); forensic triage prioritizes recall (low FN). Calibrated scores are prerequisites for cost-sensitive threshold optimization — you cannot set an informed threshold if scores don’t represent actual probabilities.

Recommendation for the field: Report ECE or reliability diagrams alongside AUC and accuracy. Track calibration quality during training, not just after. This is a low-cost addition (one extra metric, one extra plot) that provides substantially more deployment-relevant information.

Q39: What did you learn from this project beyond the technical results?

Answer: Three meta-lessons:

1. Engineering matters more than architecture for applied ML. The decisions that had the most impact were not architectural choices (Transformer vs MLP, Focal Loss vs BCE) but engineering ones: switching audio loading from librosa to torchaudio to handle corrupted MP4s, designing resumable manifests to survive cloud termination, implementing two-phase training to protect pretrained features. Published papers focus on architectural novelty; in practice, data pipeline robustness often dominates performance. The 8,475 missing/corrupted videos in the dataset were a lesson in the gap between benchmark descriptions and real-world data quality.

2. Resource constraints shape research conclusions. The 5-epoch training cap (cloud GPU costs), the validation-split-only training (storage limits), and the 100-video test set (time constraints) were not methodological choices but practical necessities. The conclusions I can draw — that earlier checkpoints may be better calibrated, that audio_modified is the hardest type — are bounded by these constraints. Recognizing and clearly stating these bounds is more honest than overclaiming.

3. Infrastructure management is a research skill. Managing Vast.ai instances, SCP file transfers, Google Drive for Colab checkpoints, W&B logging, and multiprocessing feature extraction across 28 workers was more time-consuming than model design. Model 1’s corrupted download — a 30-second file size check that wasn’t done — taught me that operational diligence is as important as algorithmic correctness. Future projects should budget significant time for infrastructure, not just modeling.
